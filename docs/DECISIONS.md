# 주요 설계 결정

| 결정 | 근거와 영향 |
| --- | --- |
| 현재 작업 디렉터리를 저장소 루트로 사용 | 비어 있는 작업 공간에서 추가 중첩 디렉터리 없이 설치한다. Git 초기화는 로컬에서만 수행한다. |
| 패키지 내 리소스와 작은 모듈 | 독립 wheel을 설치해도 규칙을 사용할 수 있도록 문서 원본을 패키지 안에 둔다. Profile과 Stack 정의는 카탈로그 한 파일에, 역할은 별도 카탈로그에 모은다. 사용되지 않는 디렉터리와 하위 패키지는 만들지 않는다. |
| `argparse`, Pydantic, PyYAML, uv_build | 외부 CLI 프레임워크와 템플릿 실행 엔진 없이 필요한 기능을 제공한다. 스키마 산출물은 모델에서 생성한다. |
| 기존 루트 지침 보존과 가이드 연결 | 기존 지침 파일에는 자동 병합이나 블록 삽입을 하지 않는다. `adopt`는 기본으로 미리보기이며 `--apply`로 반영한다. `update`는 기본 미리보기이며 `--apply`가 쓰기 의도를 나타낸다. |
| 관리 파일 충돌은 사용자 해결 | 삼방향 병합이나 강제 덮어쓰기를 제공하지 않는다. 출력이 더 이상 필요 없을 때도 보관본을 만든 다음 수정되지 않은 관리 파일만 제거한다. |
| 역할 정의와 실행 분리 | 자동 실행에는 도구별 실행 권한, 비용 및 인증 정책이 필요하다. 현 버전은 문서 기반 작업 분배와 worktree를 제공한다. |
| 초기 배포 라이선스 MIT | 자체 작성 파일에 MIT를 적용한다. 외부 저장소 코드는 포함하지 않는다. |
| 릴리스와 하위 호환성 | SemVer를 사용한다. `0.x`에서 호환성 변경은 마이너 버전과 CHANGELOG에 명시한다. 설정과 잠금 형식은 독립된 스키마 버전을 가진다. |
| 중복 카탈로그 항목 병합 | Git·컨텍스트 지침을 협업 규칙에, 코딩·문서 규칙을 개발 원칙에 모았다. 일상적 제품 분석은 요구사항 Skill과 기존 역할로 수행한다. 개별 전문 검증 Skill은 반복 사용 근거가 생기면 추가한다. |
| 소스 배포의 검증 자료 포함 | 소스 배포에는 예제·테스트·스키마·개발 도구를 포함한다. wheel은 실행 코드, 규칙과 릴리스 노트만 포함한다. |

## 0.1.1

- 관리 프로젝트 탐색은 가장 가까운 Lock 또는 중단된 트랜잭션을 찾는다. 별도 Git 체크아웃과 명시적 `--path`는 작업 대상의 경계로 처리한다.
- 설치 검증은 Lock을 기준으로 수행한다. 구성 변경은 적용 후 품질 명령을 실행할 수 있으며, CLI 버전 변경에서 생긴 출력 차이는 업데이트 계획에서 확인한다.

## 0.1.2

`inspect --suggest-rules`는 알려진 설정의 선언과 경로를 근거로 규칙 초안을 출력한다. 적용은 프로젝트 소유의 규칙 문서에서 검토 후 진행한다.
