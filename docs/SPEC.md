# 기능 요구사항

## 사용자 흐름

1. 개발자는 `init`에서 유형, 스택, 도구와 최소·표준·확장 구성을 선택한다. 프로젝트 목적, 규모, 배포 환경, 팀, 보안과 테스트 요구를 YAML로 기록한다. 같은 입력과 Toolkit 빌드는 같은 관리 파일을 생성한다.
2. 기존 프로젝트에는 `inspect`와 `adopt`를 사용한다. 감지 근거와 계획을 확인한 뒤 명시적으로 적용한다. 기존 코드, CI, 문서, 루트 지침, 사용자가 만든 Skills의 소유권을 보존한다.
3. 프로젝트는 Git에 YAML 구성, `toolkit.lock`과 관리 파일을 저장한다. 선택 요소를 조정하거나 설치한 Toolkit 버전을 바꿀 때 `update --dry-run`과 `diff`를 먼저 실행한다.
4. `validate`는 구성과 관리 파일 일관성을 검사한다. `validate --run`은 로컬에서 승인한 품질 명령을 실행한다. 필수 명령 실패는 비정상 종료다.
5. 필요에 따라 문서, 작업별 인수인계, 작업 크기별 역할 계획, Git worktree를 활용한다. 역할 정의와 작업 영역은 사용자가 에이전트에 전달한다.

## MVP 인수 기준

- A~E 신규 조합과 F 기존 프로젝트 도입·수정·업데이트 시나리오가 CLI 테스트를 통과한다.
- 공통 규칙, 최소 열 개 Skills, 프로젝트와 스택 선택, 역할 및 품질 분류가 실제 생성물로 조합된다.
- Codex, Claude Code, Grok Build용 공식 검색 경로와 수동 Markdown 사용 방식이 문서화된다.
- 등록된 도구별 역할 변환을 검증하고, 사용자 파일 충돌·경로 탈출·관리 파일 변경을 차단한다.
- 설정 스키마, SHA-256 잠금, 계획 출력, 복구 경로, 설치 가능한 wheel, OS별 CI를 제공한다.
- 첫 적용은 README의 명령으로 재현된다.

Docker worker, 외부 Skills 설치, 실행 이력 분석, 유료 에이전트 호출, 정책의 자동 개선은 후속 범위다.
