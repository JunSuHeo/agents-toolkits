# requirements-analysis

요청을 확인 가능한 동작과 인수 기준으로 정리한다.

## 입력과 선행 조건

- 사용자 요청, 현재 동작과 이해관계자 제약
- 관련 제품 문서와 실제 사용 경로를 읽는다.

## 적용 범위와 도구

할당된 프로젝트와 명시적으로 허용된 범위에서만 적용한다. 사용 도구는 읽기, 검색, 사용자 질의다.

## 절차

1. 행위자, 운영 조건, 성공 경로와 예외를 구분한다.
2. 각 요구를 관찰할 수 있는 인수 조건으로 표현하고 해당 계약을 찾는다.
3. 우선순위, 범위 밖 항목과 해결되지 않은 결정의 소유자를 기록한다.

## 인수 기준 예시 — “월별 거래를 내려받고 싶다”

| 조건 | 사용자 행동 | 관찰할 결과 |
| --- | --- | --- |
| 대상 월에 거래가 있음 | 3월 CSV 다운로드 | 첫날과 마지막 날의 거래가 포함되고 4월 거래는 제외된다. |
| 결과가 비어 있음 | 빈 달 다운로드 | 합의한 빈 결과 형식으로 응답한다. 헤더만 있는 CSV가 요구인지 확인한다. |

월의 경계를 UTC로 잡을지 사용자 시간대로 잡을지에 따라 같은 거래가 다른 파일에 들어간다. 기존 화면의 기준을 찾아 근거로 제시하고, 제품 규칙이 정해지지 않았다면 결정할 사람과 영향을 받는 사례를 기록한다.

## 출력과 검증

요구사항, 인수 조건, 위험과 열린 질문. 각 필수 요구에 검증 방법과 예상 결과가 있다.

## 실패 처리와 제한

승인이 필요한 불확실성은 구현 가정으로 확정하지 않고 결정 필요 항목으로 남긴다. 프로젝트의 보안 및 승인 정책을 따른다. 선행 Skill 의존성은 없다.
